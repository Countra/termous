# Agent 工具导航与循环纠错验收

后续已将本次桌面故障修复扩展为全部内置工具共用的能力契约与执行反馈，见[统一能力架构及最新验收](./agent-capability-architecture.md)。下文保留桌面专项的原始验收记录。

## 设计边界

本次沿用 Electron Worker 中的 pi Agent、Core 工具和持久化链路。普通重复检测只提示并继续；不按次数中止、不隐藏被重复调用的普通工具。权限、输入结果不确定保护、资源释放门禁和用户主动启用的执行预算仍分别生效。

普通桌面截图产生 `screenshot_id`，固定 workflow 快照产生 `snapshot_id`。能力目录显式关联工具、用途及完整 Skill URI；成功截图只预加载准确候选声明，不自动执行快照。相同有效观察或同类失败第三次提示，2～4 步短周期也参与检测；同一模式按 3、6、12…退避。

每次请求附带一份由实际回执构成的有界执行摘要。压缩继续按模型容量 80% 与输出预留规则触发，普通循环不额外发起模型摘要请求。动态工具、图片和补充摘要均计入请求估算；Core 确认检查点提交前不替换历史。检查点中的执行状态不恢复历史授权。

主库 Goose 51、Agent 库 4、workflow 库 2 各自独立演进，本次只使用现有事件 JSON 和 checkpoint details，不新增迁移。

## 实际故障回归

`electron/agent/test-support/desktop-loop-incident.json` 包含原故障的 62 次脱敏调用，其中 50 次普通截图。夹具只保留检测所需字段和图片哈希，不包含原图、凭据或私密正文。测试覆盖新截图 ID、帧号和到期时间变化，成功与无新帧错误交替、重复 Skill、失败参数变化及工具往返。

真实验收还发现桌面路由的错误提示不完整：`attach` 参数正确但本轮尚未查询时，也只返回“参数不一致”；历史继续任务使用旧附着时则只返回空的可用 ID 列表。现已保留原校验，并补充准确的只读查询前置步骤和当前目标参数；下一请求加载所需查询声明。回归同时覆盖 Responses 与 Chat Completions，验证旧附着没有派发，新附着必须经过本轮查询与真实回执。

## 验收方式

使用本地 800×600 VNC 协议夹具，经过真实 Core、Electron 托管桌面、utilityProcess Worker 及已配置的 `glm-5.3-flash`。模型凭据仅经过既有 bootstrap 认证链。测试不输入键鼠、不访问真实远端。

五个独立测试包括三个新会话和两个有历史的继续任务。每轮最多 240 秒、24 次模型请求；这是验收程序限制，不是产品重复检测策略。第三项要求先连续普通截图三次，再创建固定快照并放大查看左上角区域，必须实际出现重复提示。历史任务先观察并结束，再以同一夹具的新桌面会话继续，检验历史 ID 不会恢复权限。

验收成功要求实际成功回执中存在 `snapshot_id`，随后从同一快照放大查看左上角 100×100 区域，不能仅按 `tool_completed` 或模型自述判断。

在仓库父目录现有 `TEMP` 下管理 Go build/mod/tmp、Node 缓存和所有验收产物，pnpm 缓存保持默认。Core 使用现有 `dev-data/.termous`，不另建开发数据目录。

本地运行前启动开发 Core（8122，既有开发认证）并完成 `pnpm build:renderer`；随后在 `web` 目录运行：

```powershell
node scripts/desktop/fixture-server.mjs
```

另一个终端运行：

```powershell
pnpm exec electron scripts/agent/run-progress-acceptance.mjs --keep-sessions
```

验收程序使用 `http://127.0.0.1:5191/` 加载托管桌面；开发 Core 保持既有来源校验，不为 `file://` 或空来源放宽权限。最终报告位于 `TEMP/runtime/agent-progress/report.json`，保留会话用于界面复核；`--probe` 只运行首项，不能代替五项验收。

自动化测试验证请求实际声明、补充摘要不累加、工具和图片变动后的用量失效、压缩提交失败及恢复，而不只检查界面百分比。有限样本和提示策略不能保证任意模型、任意任务永不循环。

## 验收中的失败记录

失败记录保留在同一输出目录，不能将其计入通过样本：

- `initial-failed-report.json`：验收程序最初从 `file://` 加载托管桌面，开发 Core 的来源校验返回 403。调整为既有本机 HTTP 开发页面后重跑，未修改 Core 来源策略。
- `origin-fixed-report.json`：首项实际完成了快照及查看，但验收脚本没有解析带说明前缀的回执元数据；后续共用桌面失效。修正回执解析，并让独立测试使用独立桌面。
- `precondition-failed-report.json`：暴露本轮查询前置条件缺失却只提示参数错误，以及历史附着重试问题；两项继续任务到达独立验收上限。第三项虽完成截图纠错和固定帧查看，但原提示未要求放大，因此未满足验收中要求放大的判定。后续补齐前置步骤导航，并明确测试中的 2 倍放大目标。

这组记录区分验收设施问题、模型执行结果和产品问题；超限不会导致产品新增重复次数硬限制。

## 桌面专项第一阶段真实验收结果（2026-10-15）

最终 `glm-5.3-flash` 验收五项全部通过，合计七轮、53 次模型请求：

| 测试 | 场景 | 模型请求数 | 实际结果 |
| --- | --- | --- | --- |
| 1 | 新会话直接创建固定快照 | 7 | 创建成功，同一快照局部放大成功 |
| 2 | 先观察，再制作固定素材 | 8 | 普通观察后转向 workflow，局部放大成功 |
| 3 | 连续三次相同普通截图 | 10 | 第三次提示，创建固定快照后更新为恢复，2 倍放大成功 |
| 4 | 观察后结束，带历史继续 | 6 + 8 | 旧附着被拒后查询当前会话、重新附着，完成快照及放大 |
| 5 | 另一独立历史继续任务 | 6 + 8 | 完成本轮重新核验和附着，快照及放大成功 |

第三项实际事件序列在第 359 号事件报告重复三次；后续请求声明包含 `termous.desktop_workflows.captures.create`，执行摘要为 461 Token，并记录了 64 位十六进制上下文指纹。随后同一模式从 `detected` 更新为 `progressed`。脱敏请求诊断位于 `TEMP/runtime/agent-progress/request-evidence.json`。

In-app Browser 检查了真实 Core 会话：展开恢复记录、准确候选入口、约 17k / 262k 的上下文占用、209,715 Token 压缩阈值和模型用量校准来源。刷新后只显示一条合并后的 `progressed` 记录。界面截图位于 `TEMP/runtime/agent-progress/ui-recovery.jpg`。

本轮真实验收任务较短，未触发容量压缩；长上下文、检查点提交失败与恢复由自动化回归覆盖。开发库保留验收会话与临时主机供复查；曾有临时主机清理请求被自动审批拒绝，未绕过删除。
