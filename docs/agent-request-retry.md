# AI 请求重试

普通回答、工具续轮和压缩摘要使用 pi `retryAssistantCall`，初次请求失败后最多额外重试三次，退避为 1、2、4 秒。只重试官方判定可恢复、且当前请求尚未产生非空正文、思考或工具调用内容的错误；空文本块和流开始不算内容。明确的鉴权失败和上下文溢出优先排除，避免诊断文字中的重试提示触发误判。已有输出后断流、用户取消及摘要校验失败沿用最终失败或取消流程。

## 执行与用量

- Worker 的独立重试适配器包装现有受限 Provider 通道；底层 HTTP 重试和压缩算法的额外重试保持关闭，禁止次数叠加。
- 每个逻辑请求固定模型、参数和上下文。重试不会重新执行工具、消费排队指令或重跑上下文压缩。
- 中间无内容失败不进入 Agent 消息终态；只有最终结果交给现有桥接层，防止提前结束 Run。
- 被替代失败尝试在下一次实际请求开始时计量，最终响应沿用现有计量。退避期间取消不会重复累计；摘要失败消耗也纳入摘要及本轮统计。
- 最终 `AssistantMessage.usage` 只代表最后一次物理请求，不得填入多次尝试累计值，以免污染上下文窗口占用。

## 状态与协议

协议版本为 7。`retry` 活动经已有 Runtime 事件接口写入 Core，持久化后通过工作区 WebSocket 推送；不增加 Run 主状态、HTTP 接口或数据库表。

活动状态为 `waiting`、`requesting`、`completed`、`failed`、`cancelled`。同一逻辑模型请求使用稳定 `retry_id`；`purpose` 区分 `response` 和 `compaction`。`attempt` 表示已经开始的额外请求次数，所以第一次等待为 0、开始第一次重试为 1；界面等待时显示 `attempt + 1`，终态显示实际次数。`max_retries` 固定为 3。

重试活动锚定 assistant 消息及片段位置。历史消息按页批量加载活动，实时事件与历史归并后更新同一行。Core 在取消、异常退出和重启恢复时收口未完成活动，避免历史显示永远重连中。

停止信号通过 IPC 异步到达 Worker；Core 在 `stopping` 期间接收已在传输中的重试报告并保持停止状态。已提交事件的幂等重放不受后续活动状态影响。含重试活动的本机状态必须保留连续事件链，缺失事件时在恢复事务提交前拒绝导入。

## 错误与展示

活动保留最近一次 pi `errorMessage` 的原语言和换行，沿用现有服务地址及凭据脱敏、清理不可显示控制字符并限制为 4 KiB。错误以纯文本展示，不执行其中的 Markdown、HTML 或链接。暂时失败不覆盖 Run 的最终错误。

会话内使用紧凑 Wi-Fi 活动行，等待与请求中轻微呼吸，减少动态效果时停止动画。错误默认两行，可展开；成功后收起详情。停止按钮始终遵循现有运行状态，重试不会让队列提前推进。
