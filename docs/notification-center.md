# 消息中心与系统通知

Core 是消息事实和已读状态的唯一来源。Renderer 与 Electron 分别订阅 Core WebSocket，不通过页面组件互相转发完成事件。现有 Agent 和文件任务执行、重试和 Toast 保持原有职责。

`common/contracts/notification.ts` 定义纯合同、解码、展示模板和受控跳转目标。`entities/notification` 合并权威快照与增量；`features/notifications` 负责订阅协调和本机偏好；`widgets/notification-center` 展示顶部铃铛和右侧抽屉；`app/notification-runtime` 装配订阅、状态操作与激活交接。设置页面以插槽装配通知设置，避免 feature 横向依赖。

`common/notification-stream` 是 Renderer 和 Electron 共用的消息订阅连接模块，仅处理既有通知协议。每次连接须在 10 秒内收到首个 `snapshot`，增量不能代替首帧；失败后按 1～30 秒有界退避重连，并在有效快照后重置退避。错误、首帧超时和停用都会立即隔离旧回调、释放定时器及连接，不等待浏览器迟迟不来的 `close`。Core 的 WS Ping／Pong 负责空闲探活，不产生业务消息；已经就绪且空闲的连接不会因首帧期限重连。主进程重连仍重新读取 Core 配置，不缓存过期地址或凭据。

`electron/notifications` 管理原生投递、偏好、Core 订阅和 IPC。本地和远端消息统一通过主进程的 `BrowserWindow.getFocusedWindow()` 判断应用焦点：主界面、AI 助手、桌面自动化、远控等任意窗口聚焦时不提醒；所有窗口均失焦时才允许投递，主窗口无需最小化或隐藏。通知不再依赖远端会话的可见状态上报。首次快照仅建立水位，重连补齐不超过两分钟的新结果；应用侧水位防止重复投递。前台收到的消息不会在之后失焦时补发。文件消息在两秒内合并，最多保留三个原生对象；最终投递前再次检查应用焦点与偏好。不支持或投递失败不影响 Core 历史，也不自动循环重弹。

点击通知唤起主窗口，激活意图最多保留 16 个；Renderer 先订阅激活提示再读取 pending，完成已读写入后 acknowledge。原生消息关闭或弹出不标记已读。合并提醒进入文件消息分组，单项定位既有 Agent 会话或传输记录；目标不可用时保留摘要，不创建、重连或重试任务。

单项系统消息直接定位目标，不先打开消息抽屉；只有合并消息或目标不可用时才展示消息中心。审批文案简化为“有命令待审批”等类别提示，保留来源名称，具体操作在原审批窗口核对。

消息抽屉在显示及关闭动画期间以 `no-drag` 保证遮罩和按钮可点击，动画完成后销毁 Portal。不能保留带整屏禁拖拽区域的隐藏容器，否则 Electron 顶栏会失去窗口拖动能力。筛选与消息状态保存在抽屉外，重新打开继续保留；手动关闭时仍将焦点返回铃铛。

定位完成与已读、激活确认分步处理。后两步失败时保留待确认意图和错误状态，不重新打开抽屉；当前 Renderer 按 1～30 秒有界退避自动补交接，不依赖下一条通知，也不重复切换页面。成功后停止重试，订阅停用或卸载后取消重试；异步定位结果不再更新抽屉或写入已读。传输定位会恢复全部筛选，目标行出现并获得焦点后才消费定位请求，避免列表晚到或连续点击同一任务时丢失定位。

两秒合并等待期间，Electron 用权威快照移除已经读过或清理的待投递文件结果；合并数量和点击目标均由剩余结果生成。

通知偏好保存在 userData 下 `notification-preferences.json`，严格校验总开关、AI 助手、文件、审批、云服务五个布尔开关；旧偏好保留原值并默认开启缺少的审批和云服务类别。通过同目录临时文件与 rename 原子更新，串行写入避免并发覆盖。它不随配置备份迁移。浏览器仅显示 Core 消息中心。

通知对外统一使用“AI 助手”，内部类型仍为 `agent`。列表分开展示结果、会话标题或文件名、正文概览或传输统计；系统通知正文包含相同摘要。标题最多 80 个 Unicode 字符、概览最多 160 个字符，由 Core 限长，Renderer 以纯文本展示。文件摘要保留传输量、完成数、跳过项及不确定结果。

审批使用独立 `approval` 来源和偏好，后台立即提醒，无需等待运行结束。Core 对账后移除已经失效的审批提醒，Electron 同时释放对应原生对象。点击时校验当前审批 ID 和有效期，并通过现有审批协调器选择该请求；主机密钥确认仍优先。点击通知不批准命令，也不重新创建失效请求。

原生通知遵循系统通知权限、勿扰模式及声音策略。测试使用受控通知对象验证策略，不将 `Notification.show()` 成功视为用户已看到消息；Windows、macOS 和 Linux 的打包体验需要分别验收。
