# 本地 Core 启动与心跳期限

Electron 在主进程中管理托管 Core 的启动与心跳，Renderer 渲染或后台窗口限频不承担保活职责。时间策略集中于 `electron/coreLifecyclePolicy.ts`。

| 检查 | 期限 | 到期行为 |
| --- | --- | --- |
| 运行期心跳发送 | 就绪后立即发送，之后每 10 秒 | 同一代次最多一个请求在途 |
| 单次本机请求及启动探针 | 5 秒，包含探针响应体读取 | 允许下次重试，单次失败不判定进程失联 |
| 运行期持续失联 | 距最后成功心跳 60 秒 | Electron 报告 `CORE_HEARTBEAT_TIMEOUT`；Core 未收到心跳时执行既有退出清理 |
| 普通启动 | 每个实例 120 秒 | 报告 `CORE_START_TIMEOUT` 并清理所属进程 |
| 数据库完成后的服务初始化 | 首次进入 `services` 后 120 秒 | 同上，启动心跳不刷新固定期限 |
| 数据库处理 | 保留安全等待，不套用普通启动硬期限 | 60 秒提示较慢；60 秒未收到有效启动快照提示无法确认，继续等待明确结果 |

Core 的运行期心跳窗口从 `runtime.Start` 开始，初始化耗时不计入首次心跳期限；重复调用 `Start` 不能续期。内部时间差保留 Go 单调时钟，对外时间仍为 UTC。Electron 传入的 `TERMOUS_HEARTBEAT_TIMEOUT` 与自身失联窗口一致；独立 Core 默认也是 60 秒，已有显式环境配置继续有效，未启用心跳的外部 Core 不受托管生命周期影响。

Electron 的心跳、启动期限和退出等待使用单调时钟，状态快照仍记录真实日期，系统校时不会缩短或延长保护窗口。Core 在同一临界区完成心跳到期判定和关闭提交；已接受的新心跳不会被旧的到期结果覆盖。

普通启动和 `services` 分别计时，不承诺数据库处理包含在两分钟总期限内。明确进程退出、权限错误或结构化启动失败仍立即结束等待；只对端口冲突保留既有有限重试。启动探针返回后再次检查取消、所属进程和期限，迟到结果不能放行。停止、恢复和替换 Core 后，旧心跳不能更新新实例的健康时间或触发错误。

固定启动期限到期后的服务阶段事件不能重新开启等待；明确失败仍保留原始原因。终态失败前首次确认正在处理数据库时，继续沿用数据库安全等待，避免管道消息迟到导致中断迁移；失败终态不能被后续快照重新打开。已进入 `closing/closed` 的 Core 即使仍能响应 HTTP，也不能作为就绪实例放行。

退出前读取维护状态的五秒期限覆盖完整 JSON 正文，读取完成后才释放连接；读取失败、正文停滞或合同无效时保留应用和心跳。可取消任务请求取消，任务已经进入不可取消的写入阶段时继续等待明确完成。仅需状态码的心跳、取消和关闭请求返回状态快照，不把已释放连接的 Response 交给后续代码读取正文。

这些期限只用于本地 Core 生命周期，不改变业务 HTTP 超时、远控媒体确认、HDR 处理或终端/WebSocket 的独立期限。

回归重点：45 秒慢启动、接近两分钟的边界、心跳不能无限延长启动、长数据库迁移、45 秒暂时失联后恢复、持续一分钟失联、系统校时、心跳续约与到期并发、启动期间取消、旧实例迟到响应、维护状态慢响应和安全关闭/恢复。
